# 智能客户反馈分析与工单自动化管理平台

> 项目名称：Smart Feedback & Ticket Automation Platform  
> 文档定位：开发设计基线（v1.0）  
> 依据：项目需求说明书 v1.0  
> 状态：待评审，尚未进入代码实现

## 1. 项目目标与边界

平台面向中小型 SaaS 团队，将来自网页表单和外部平台的客户反馈统一沉淀为可追踪工单，并通过 n8n 与大模型实现自动编排和辅助分析。

核心目标是建立如下闭环：

```text
接收反馈 → 校验/去重 → 保存原始数据 → AI 分析 → 规则定级
        → 创建或更新工单 → 人工处理 → 超时提醒 → 统计看板
```

本项目采用的关键边界如下：

| 事项 | 归属 | 设计原则 |
|---|---|---|
| 参数校验、幂等、优先级最终裁决、状态迁移、数据一致性 | Spring Boot | 由确定性代码负责，不信任外部输入 |
| 外部 Webhook、定时扫描、失败重试编排 | n8n | 负责流程连接，不持有核心业务真相 |
| 分类、摘要、优先级建议 | 大模型 API | 仅提供建议，输出必须校验 |
| 原始反馈、工单、分析和审计数据 | MySQL | 作为可追溯的业务事实来源 |
| 提交、查询、处理、统计 | Web 前端 | 保留人工审核和处理入口 |

初期不引入微服务、Kafka、Kubernetes、向量数据库或复杂多 Agent 架构。

## 2. 角色与核心场景

| 角色 | 主要职责 |
|---|---|
| 客户/外部系统 | 提交反馈或推送事件 |
| 客服人员 | 查看、筛选和跟进工单 |
| 开发人员 | 处理 BUG，补充处理备注 |
| 管理员 | 调整优先级、管理工单状态、查看统计与超时提醒 |
| n8n | 接收外部事件、发起分析、扫描超时工单 |

### 2.1 关键业务规则

1. 表单标题必填，最长 100 字符；内容必填，最长 2,000 字符；来源必须在白名单内。
2. `createdAt` 必须由服务端生成，客户端传入的时间不作为业务创建时间。
3. 同一 `source + externalId` 只能对应一条外部反馈。网页表单没有 `externalId` 时，每次有效提交创建新反馈。
4. 原始反馈成功保存后，分析失败不得回滚或丢弃原始数据。
5. 高风险关键字命中的确定性规则优先于 AI 的建议优先级：即使 AI 建议为 `LOW`，最终仍为 `HIGH`。
6. 管理员可以人工调整优先级，但必须填写调整原因并记录审计日志。
7. 工单业务状态和 AI 分析状态分开维护。
8. 超时提醒必须幂等；同一工单、同一种超时事件只能产生一条有效提醒。

## 3. 总体架构

```text
┌──────────────┐    ┌──────────────────┐
│ 网页表单/后台 │───▶│ Spring Boot API  │────────┐
└──────────────┘    └──────────────────┘        │
                                                   ▼
┌──────────────┐    ┌──────────────────┐    ┌────────┐
│ 外部平台事件  │───▶│ n8n Webhook 流程  │───▶│ MySQL  │
└──────────────┘    └────────┬─────────┘    └───┬────┘
                              │                  │
                              ▼                  ▼
                       ┌────────────┐    ┌────────────────┐
                       │ 大模型 API  │    │ Spring Boot API│
                       └────────────┘    └────────────────┘
                              │                  │
                              └────分析结果───────┘

              n8n 定时任务 ──▶ 查询待分析/超时工单 ──▶ 写回处理结果
```

建议采取“保存后异步分析”方案：Spring Boot 在事务中保存反馈、工单与待分析状态；随后由 n8n 调用待分析接口取得任务并回写分析结果。该方式在 n8n 或模型暂时不可用时仍能保存用户反馈，且支持可控重试。若后续需要更快响应，可在创建后通过 Webhook 触发 n8n，但仍应保留定时扫描作为补偿机制。

## 4. 领域模型与状态机

### 4.1 枚举定义

| 名称 | 取值 |
|---|---|
| 工单状态 `ticketStatus` | `NEW`、`IN_PROGRESS`、`RESOLVED`、`CLOSED` |
| 分析状态 `analysisStatus` | `PENDING`、`PROCESSING`、`SUCCEEDED`、`FAILED` |
| 分类 `category` | `BUG`、`FEATURE`、`QUESTION`、`OTHER` |
| 优先级 `priority` | `HIGH`、`MEDIUM`、`LOW` |
| 来源 `source` | `WEB`、`EXTERNAL`（后续按需扩展） |

### 4.2 工单状态迁移

```text
NEW ───────────────▶ IN_PROGRESS ───────────────▶ RESOLVED ───────────────▶ CLOSED
 │                         │                          │
 └─────────────────────────┴──────────────────────────┴── 管理员允许时可退回 IN_PROGRESS
```

所有状态变更均写入操作日志。`CLOSED` 前应保证已处于 `RESOLVED`；如业务允许关闭未解决工单，应额外记录关闭原因。

### 4.3 优先级规则

优先级计算顺序如下：

1. 对标题和内容进行标准化后匹配强制高风险关键字（例如“数据丢失”“支付失败”“无法登录”）。命中即为 `HIGH`。
2. 未命中高风险规则时，采纳经校验的 AI 建议优先级；缺失或非法时默认 `MEDIUM`。
3. 管理员人工调整可覆盖系统优先级，并必须记录 `previousPriority`、`newPriority` 和 `reason`。

选择规则优先的原因是：高风险词属于可审计、确定性的安全与业务约束，而 AI 输出存在不稳定性，不能降低已明确识别的风险。

### 4.4 SLA

| 优先级 | 处理时限 | 截止时间计算 |
|---|---:|---|
| HIGH | 4 小时 | `created_at + 4h` |
| MEDIUM | 24 小时 | `created_at + 24h` |
| LOW | 72 小时 | `created_at + 72h` |

初版按自然时间计算。若后续需要工作日/节假日 SLA，应将计算器抽象为独立领域服务。

## 5. 数据库设计

### 5.1 `tickets`：反馈与工单主表

| 字段 | 类型建议 | 约束/说明 |
|---|---|---|
| `id` | BIGINT | 主键 |
| `feedback_id` | VARCHAR(36) | 内部公开 ID，唯一 |
| `title` | VARCHAR(100) | 非空 |
| `content` | VARCHAR(2000) / TEXT | 非空，保存原始内容 |
| `source` | VARCHAR(32) | 非空 |
| `external_id` | VARCHAR(128) | 外部事件 ID，可空 |
| `ticket_status` | VARCHAR(32) | 非空，默认 `NEW` |
| `priority` | VARCHAR(16) | 非空 |
| `priority_source` | VARCHAR(32) | `RULE` / `AI` / `MANUAL` |
| `due_at` | DATETIME | 非空 |
| `overdue_at` | DATETIME | 可空，首次超时标记时间 |
| `created_at` / `updated_at` | DATETIME | 服务端维护 |
| `version` | BIGINT | 乐观锁版本号 |

约束与索引：

- 唯一索引：`uk_tickets_source_external_id (source, external_id)`。MySQL 对含 `NULL` 的唯一索引允许多个空值，符合网页反馈可重复提交的要求。
- 查询索引：`idx_tickets_status_due_at (ticket_status, due_at)`、`idx_tickets_analysis_status`（通过分析表查询或冗余状态实现）。
- 高并发重复外部事件以数据库唯一约束为最终屏障；应用捕获重复键错误后查询原记录并返回幂等结果。

### 5.2 `ticket_analyses`：AI 分析记录表

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `id` | BIGINT | 主键 |
| `ticket_id` | BIGINT | 外键，唯一（一张工单当前一条记录） |
| `status` | VARCHAR(32) | 分析状态 |
| `category` | VARCHAR(32) | 校验通过后写入 |
| `summary` | VARCHAR(500) | AI 摘要 |
| `suggested_priority` | VARCHAR(16) | AI 建议，仅供参考 |
| `reason` | VARCHAR(1000) | AI 说明 |
| `raw_response` | TEXT | 原始响应，用于排查（注意脱敏） |
| `error_code` / `error_message` | VARCHAR | 失败原因 |
| `attempt_count` | INT | 尝试次数 |
| `processed_at` | DATETIME | 最终处理时间 |

### 5.3 `ticket_events`：操作与审计事件表

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `id` | BIGINT | 主键 |
| `ticket_id` | BIGINT | 外键 |
| `event_type` | VARCHAR(64) | 如 `STATUS_CHANGED`、`PRIORITY_CHANGED`、`OVERDUE_MARKED` |
| `operator_type` / `operator_id` | VARCHAR | SYSTEM、USER、N8N 等 |
| `idempotency_key` | VARCHAR(128) | 可空；超时等事件使用唯一键 |
| `payload` | JSON / TEXT | 变更前后、原因等 |
| `created_at` | DATETIME | 创建时间 |

对于超时事件创建唯一索引 `uk_ticket_events_type_key (event_type, idempotency_key)`，其中键可取 `OVERDUE:{ticketId}`，确保重复扫描不重复提醒。

## 6. API 契约

统一成功响应建议为 `{ "code": "OK", "data": ... }`，失败响应建议为 `{ "code": "VALIDATION_ERROR", "message": "...", "traceId": "..." }`。写操作应在响应中返回业务 ID 和当前状态。

| 方法 | 路径 | 用途 | 幂等要点 |
|---|---|---|---|
| POST | `/api/feedback` | 网页提交反馈 | 表单提交不强制去重；可支持可选 `Idempotency-Key` |
| POST | `/api/integrations/feedback` | n8n 写入标准化外部反馈 | 依据 `(source, externalId)` 去重 |
| GET | `/api/tickets` | 分页查询与筛选 | 支持状态、分类、优先级、是否超时 |
| GET | `/api/tickets/{id}` | 查询工单详情 | 返回原始反馈、分析、事件 |
| PATCH | `/api/tickets/{id}/status` | 更新工单状态 | 校验合法状态迁移，记录事件 |
| PATCH | `/api/tickets/{id}/priority` | 管理员调整优先级 | `reason` 必填，记录事件 |
| GET | `/api/tickets/pending-analysis` | 获取待分析任务 | 仅供 n8n/内部调用，需认证 |
| POST | `/api/tickets/{id}/analysis` | 写入 AI 分析结果 | 校验 JSON 字段与分析状态 |
| POST | `/api/tickets/{id}/analysis/failures` | 写入分析失败结果 | 不影响原始工单 |
| POST | `/api/jobs/overdue-check` | 执行超时扫描 | 幂等创建超时事件 |
| GET | `/api/tickets/overdue` | 查询超时工单 | 供后台展示 |
| GET | `/api/statistics` | 获取统计数据 | 返回总量、分类、待处理与超时量 |

外部写入请求必须由 n8n 以服务凭证调用；不得把数据库写权限或模型密钥暴露给前端。

## 7. n8n 工作流设计

### 7.1 外部反馈接入流

```text
Webhook → 鉴权/签名校验 → 字段映射 → 基础校验
        → 调用 POST /api/integrations/feedback → 响应调用结果
```

- Webhook 统一转换为 `source`、`externalId`、`title`、`content`。
- 对 4xx 参数错误直接返回明确失败结果，不重试。
- 对网络超时、5xx 等暂态异常按有限次数、指数退避重试；达到上限后记录 n8n 执行失败，便于人工重放。
- Spring Boot 响应丢失时，n8n 可以安全重试，因为服务端的唯一约束会返回同一业务记录而非创建新工单。

### 7.2 AI 分析流

```text
Schedule Trigger / 创建后触发
  → GET pending-analysis
  → 标记 PROCESSING
  → 调用模型（要求 JSON）
  → JSON 解析与枚举校验
  → POST analysis 或 POST analysis/failures
```

模型期望结构：

```json
{
  "category": "BUG | FEATURE | QUESTION | OTHER",
  "summary": "不超过约定长度的摘要",
  "suggestedPriority": "HIGH | MEDIUM | LOW",
  "reason": "分类和建议的简要原因"
}
```

模型 JSON 无法解析、字段缺失、枚举非法或请求超时时，写入 `FAILED` 与错误原因。工单仍保持可见，管理端提供重试或人工录入入口。成功结果写入后，后端重新执行优先级规则，不能直接用 AI 建议覆盖高风险规则。

### 7.3 超时扫描流

```text
Schedule Trigger（例如每 15 分钟）
  → POST /api/jobs/overdue-check
  → 返回新增超时数与已存在提醒数
```

超时判断和事件创建应在 Spring Boot 事务内执行；n8n 只负责触发，避免两次并发扫描造成重复提醒。

## 8. 前端页面与交互

| 页面 | 最小功能 |
|---|---|
| 反馈提交页 | 标题、内容、来源提交；显示校验错误与提交成功 ID |
| 工单列表页 | 分页、按状态/分类/优先级/超时筛选、进入详情 |
| 工单详情页 | 显示原始反馈、最终优先级及来源、AI 分析与操作历史 |
| 工单处理页 | 更新状态、添加备注、管理员调整优先级并填写原因 |
| 统计看板 | 工单总数、分类分布、待处理数、超时数 |

UI 应显式标识“AI 建议”和“最终优先级”，避免操作人员误将模型建议视为最终裁决。

## 9. 可靠性、安全与可观测性

### 9.1 幂等与一致性

- 外部事件：数据库唯一约束 + 应用层重复键恢复，避免“先查后插”的并发竞态。
- 状态与优先级更新：使用乐观锁或条件更新，防止并发覆盖。
- 超时：事件幂等键 + 唯一索引，避免重复提醒。
- 分析：分析状态采用条件迁移，例如只允许 `PENDING/FAILED → PROCESSING`，防止多工作流同时处理。
- 写库事务只包含本地数据库操作；调用模型或 n8n 不放在长事务中。

### 9.2 异常策略

| 场景 | 处理方式 |
|---|---|
| 参数不合法 | 返回 400 类错误，不入库，不重试 |
| Spring Boot 不可用 | n8n 有限重试并保留失败执行记录 |
| 模型超时/不可用 | 保留反馈，记录分析失败，可手动或定时重试 |
| 模型返回非法 JSON | 标记失败，保存可脱敏的原始响应，禁止写入非法业务字段 |
| HTTP 响应丢失 | 使用服务端幂等保证重试安全 |
| 工作流中断 | 依靠分析待处理/失败状态与重试入口恢复 |

### 9.3 安全要求

- n8n Webhook 采用签名、固定 Token 或其他服务端认证；生产环境使用 HTTPS。
- 模型 API Key、数据库密码和 n8n 凭据只放置在环境变量或密钥管理系统，绝不提交到仓库。
- 日志中禁止记录完整敏感反馈、认证头和密钥；必要的模型原始响应应脱敏并限制访问。
- 管理端至少区分普通处理人员和管理员；后续可扩展 RBAC。

### 9.4 观测指标

建议记录 `traceId` 并在 Spring Boot、n8n 执行日志中透传。首期重点指标：新增反馈量、分析成功率、分析失败数、重试次数、待处理工单数、超时数、平均处理时长和重复事件命中数。
